  • contenteditable 的 tabIndex 确实是 -1，但可以被 Tab 聚焦

2. 浏览器差异说明

元素 Chrome/Edge Firefox Safari Tab 键行为
<button> 0 0 0 ✅ 可聚焦
<summary> 0 0 0 ✅ 可聚焦
contenteditable -1 -1 -1 ✅ 可聚焦（特殊处理）
普通 <div> -1 -1 -1 ❌ 不可聚焦
结论：
  • <summary> 在所有现代浏览器中 tabIndex 都是 0
  • contenteditable 的 tabIndex 是 -1，但浏览器仍然让它可以被 Tab 聚焦
  • 所以只有 contenteditable 是"tabIndex=-1 但可聚焦"的特殊情况

3. 为什么之前的说法有误？

可能的原因：

  • 规范变更：HTML 规范可能在早期版本中定义 <summary> 的 tabIndex 为 -1，后来改成了 0
  • 浏览器实现差异：早期浏览器可能返回 -1，但现代浏览器统一改成了 0
  • 文档过时：很多技术文档和教程可能基于旧版本的规范或浏览器行为
教训：技术细节应该以实际测试为准，而不是仅依赖文档或理论。 浏览器行为和规范都可能随时间变化。

5. 实际影响

这个更正对之前的结论有什么影响？

✅ 仍然正确的结论：

  • 手动设置 tabindex 会覆盖默认行为（优先级最高）
  • 不能只看 tabIndex 值判断可聚焦性（contenteditable 就是例外）
  • Tab 键只移动焦点，Enter/Space 才触发点击
  • 自定义元素需要手动处理键盘事件

❌ 需要更正的说法：

  • <summary> 的 tabIndex 是 -1 → 实际是 0
  • <summary> 是"tabIndex=-1 但可聚焦"的特殊情况 → 它就是标准的 tabIndex=0
  • 只有 contenteditable 是真正的"tabIndex=-1 但可聚焦"的特殊情况

6. 为什么 contenteditable 是 -1 但可聚焦？

现在只剩下 contenteditable 这一个特殊情况了。原因：

  • 历史原因：contenteditable 最初是 IE 的私有特性（1990 年代末），后来才标准化
  • 语义区分：tabIndex=-1 表示"这不是标准的表单控件，而是一个可编辑区域"
  • 向后兼容：改成 0 会破坏大量依赖 tabIndex === 0 判断标准控件的代码
  • 浏览器特殊处理：浏览器内部将 contenteditable 视为可聚焦，即使 tabIndex 是 -1
// 判断元素是否可被 Tab 聚焦（更正后的版本）
function isTabbable(element) {
  // 特殊情况：contenteditable
  if (element.contentEditable === 'true' && !element.hasAttribute('tabindex')) {
    return true; // tabIndex=-1 但可聚焦
  }

  // 标准情况：tabIndex >= 0
  if (element.tabIndex >= 0) {
    return !element.disabled && element.offsetParent !== null;
  }

  return false;
}
