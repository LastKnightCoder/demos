为什么 tabIndex=-1 但仍可被 Tab 聚焦？

核心原因：浏览器对某些特殊元素有内置的聚焦行为，不完全依赖 tabIndex 属性值。 这些元素虽然 JavaScript 读取的 element.tabIndex 为 -1，但浏览器仍将它们视为"可交互元素"。

1. 哪些元素有这种特殊行为？

元素 tabIndex 值 Tab 键行为 原因
<summary> -1 ✅ 可以被 Tab 聚焦 浏览器将其视为 <details> 的交互触发器
contenteditable -1 ✅ 可以被 Tab 聚焦 可编辑区域被视为输入控件
普通 <div> -1 ❌ 不能被 Tab 聚焦 非交互元素，符合预期
<div tabindex="-1"> -1 ❌ 不能被 Tab 聚焦 显式设置为 -1，只能通过 JS 聚焦

3. 技术解释

为什么会这样？

  • HTML 规范的定义： <summary> 和 contenteditable 元素在规范中被定义为 "可聚焦区域"（focusable area），即使它们的默认 tabIndex 为 -1。
  • 浏览器的实现： 浏览器在计算 Tab 顺序时，不仅看 tabIndex 属性， 还会检查元素的类型、状态、是否可编辑等因素。
  • 用户体验考虑： 这些元素具有交互性（点击展开、输入文本），如果不能用 Tab 键访问， 会严重影响键盘用户的体验。

聚焦顺序规则

  1. 正整数 tabindex（1, 2, 3...）：按数值从小到大聚焦（不推荐使用）
  2. tabindex="0" 和特殊元素（summary、contenteditable）： 按 DOM 顺序聚焦，即使某些元素的 tabIndex 读取值为 -1
  3. tabindex="-1" 的普通元素：不参与 Tab 导航，只能通过 JS 聚焦

如何判断元素是否可被 Tab 聚焦？

不能只看 element.tabIndex，应该实际测试或使用以下 JavaScript：

function isTabbable(element) {
  // 检查元素是否在 Tab 顺序中
  if (element.tabIndex < 0) {
    // 特殊元素：summary 和 contenteditable
    return element.tagName === 'SUMMARY' ||
           element.contentEditable === 'true';
  }
  // tabIndex >= 0 且未被禁用
  return !element.disabled &&
         element.offsetParent !== null; // 可见
}

4. 实际应用建议

  • 不要依赖 tabIndex 值来判断可聚焦性： 使用实际测试或检查元素类型
  • 自定义组件时显式设置 tabindex="0"： 不要依赖浏览器的特殊行为，明确表达意图
  • 焦点管理时测试所有交互元素： 包括 <summary> 和 contenteditable
